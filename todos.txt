--- homeapp file-structure redesign (multi-phase) ---

phase 1 (DONE, 2026-08-17): inserted documents/media/appdata as three sibling branches inside each workspace. core/workspaces.py::path() now returns <root>/documents instead of <root> itself; new root() gives the true workspace root. ark keeps working exactly as it did before - same .txt extension, same note/todo/evnt dirs, vendored binary completely untouched - just nested one level deeper on disk. real server data migrates automatically and idempotently on server startup (core/storage.py::_migrate_documents_layout(), same "check current shape, fix if needed, run every boot" convention as core/db.py's own schema fixups) - no manual script to run. media/ and appdata/ are not eagerly created (nothing writes to them yet) and are not git-tracked - see the two "open decision" sync items below, which are follow-ups, not blockers. verified: migration idempotency + empty-workspace handling, full Flask-test-client flow (new workspace creation, save, lock, documents scan, enable_git puts .git inside documents/ correctly), and a real dev-server run against a seeded old-layout directory - zero errors, migration fired correctly on real startup.

phase 2 (NEXT - not started): redesign ark itself. Done entirely in the real upstream repo at /home/benjamin/ark (separate git repo, NOT apps/ark/vendor in homeapp - that's a git submodule pinned to a tag of benjaminingreens/ark.git and gets overwritten by the vendor-bump process). Work happens there, gets committed/tagged, and only then does homeapp's submodule pointer get bumped (mirrors the existing "Bump ark vendor to vX.Y.Z" commits already in homeapp's history, e.g. 60589d7) - homeapp's apps/ark/routes.py, runner.py, parser.py are NOT part of this phase, they're just the Flask integration glue and don't need to change for this.

  Concrete changes needed, with current code loci (in the real ark repo, same file layout as the vendored copy):

  - scanner (scan_all(), bin/ark:1015-1043): currently only descends into note/, todo/, evnt/ subdirectories under each configured base (@TYPES = qw(note todo evnt), bin/ark:60), and within those, only opens files matching /\.txt$/ (bin/ark:1028). change: remove the directory restriction entirely - walk the whole base tree (respecting .arkrc's [bases] list same as today), filter by .ark extension instead of .txt. this is what makes "a .ark file anywhere, flat, zettelkasten-style" actually work - the atomic record is the unit, location is meaningless, organisation happens at query time via tags/queries, not via directory.

  - ark init (cmd_init(), bin/ark:82-150): currently hardcodes creating note/, todo/, evnt/ directories (bin/ark:86-88) up front. change: stop creating type directories - there's nothing to scaffold anymore since loose files can go anywhere. keep the .ark/ marker dir + default .arkrc.

  - tidy (lib/ark/commands/tidy): this is the bulk of the work. today it hardcodes a type->directory mapping (%TYPE_DIR, tidy:71-75) and writes .txt output via output_batch_path() (tidy:419-431, produces e.g. note/2026/07/note_202607_001.txt) and output_multiline_note_path() (tidy:433-446), plus a compact-merge path (tidy:694/705) using the same pattern. source-file selection is also type/extension-gated (wanted_by_level, tidy:247-267, .txt filter at tidy:251; is_item_month_file's note|todo|evnt regex, tidy:233-236).
    new behaviour:
      - one flat output folder instead of three type directories. default name "ark", but configurable per-workspace via a new .arkrc key (e.g. output_dir= under [defaults] - the .arkrc parser, load_arkrc() in lib/ark/core.pl:175-300, already accepts arbitrary free-form [defaults] key=value pairs with zero parser changes needed, so this is just "read one more key" inside tidy, not new plumbing).
      - consolidated batch filenames become DATE-FIRST, not type-first: e.g. 2026-07-note.ark, 2026-07-todo.ark - NOT note-2026-07.ark. this matters: date-first keeps a directory listing chronological regardless of type; type-first would silently re-sort the folder alphabetically by type again, undoing the whole point of dropping note/todo/evnt. same record-count-cap / numeric-suffix batch-splitting behaviour tidy already has today, just with the filename order swapped and .ark extension.
      - loose, untidied, or hand-created .ark files anywhere in the workspace are NEVER renamed or moved by anything except tidy sweeping them into the output folder - their filenames stay exactly whatever the user gave them, always. only tidy's own consolidated batch output follows the naming convention. this was explicit and deliberate: meta stays entirely inside the file body, never in the filename, for general files - "open any .ark file, do whatever, it just works" was the whole reason filename-as-metadata was rejected earlier in this design discussion. don't reintroduce it beyond tidy's own batch files.

  - explicitly rejected ideas, don't relitigate without a good reason: (1) any kind of index/cache to speed up scanning - "the data is the index" is core to ark's philosophy, full live scan on every query is the deliberate, permanent answer, same reasoning as ripgrep having no index and still being fast enough at this scale; (2) encoding type/date/tags in the filename of general .ark files (only tidy's own batch output does this, and only type+date, never tags/status/other volatile fields).

phase 3: rename Documents -> Files. generic display only (no ark-specific tag/record parsing baked in - that stays inside the dedicated ark app, which remains the place for an ark-focused view). browses documents/ + media/ branches. basic unix-like commands only (browse/filter/search, maybe rename/move/delete) - no shell-style invocation of other apps' commands from inside files; that stays via HOME's normal app-switcher, to avoid files needing per-app awareness.
