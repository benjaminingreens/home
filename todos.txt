notes on this file: priority = how breaking the change is x how central it is to homeapp/ark's philosophy (plain text, local-first, "the data is the index", generic files, minimal/command-driven apps).
  1 = breaking (incompatible with current data/workspaces) AND philosophy-critical
  2 = breaking, not philosophy-critical
  3 = non-breaking, but philosophy-critical
  4 = neither
not everything below is committed to - several are half-formed ideas, marked as such. see issues.txt for reports of current behaviour being wrong, as opposed to new work.

--- priority 1 ---

todo: git pull/push (core/workspaces.py, apps/ark/runner.py::auto_sync/is_git_linked) is scoped to the app's own data folder (e.g. a workspace's ark/) only - not the workspace root proper. anything sitting beside ark/ at the true workspace root (docs/ - see the docs/-inside-ark/ incident below in history - or anything Files creates directly at the root) is completely outside git, never synced, never backed up. the real unit of sync should arguably be the workspace root, not one app's subfolder inside it - needs real review before changing, since it touches how existing linked/enabled-git workspaces are set up on disk (where .git actually lives) and would be a breaking change for anything already git-linked. flagged 2026-08-18, not investigated yet - come back to this after the Files-as-shell rework.

todo: local-first storage architecture for media/ and appdata/. currently only documents/ (ark's data) is git-synced; media/ and appdata/ aren't touched by anything yet. open sub-questions:
  - sync mechanism for media/ - git is a poor fit for binary media (no meaningful diff/merge, full-history bloat without LFS). leaning toward a simpler rsync/syncthing-style whole-file mirror instead, not designed yet.
  - sync approach for appdata/ - likely per-app rather than universal (e.g. chat is probably server-authoritative, not offline-synced like documents/media).
  - chat specifically stores data at HOME_DATA_DIR/chat/<group_id>.txt today - scoped to group, not workspace - doesn't fit "one appdata per workspace" without deciding what happens when a group has multiple workspaces.
  - whether all app data (not just chat) should live inside a workspace's userspace, or apps can keep separate siphoned-off storage - undecided.
  - the underlying goal: a fully local (offline) version of homeapp should be possible, with all of a workspace's data (documents/media/appdata) sitting together in one place rather than scattered. this is the "why" behind all of the above.
priority 1 because any real answer here changes where data physically lives on disk (breaking for anything already written), and local-first is core to what homeapp is.

--- history (file-structure redesign) ---

phase 1 (DONE, 2026-08-17): inserted documents/media/appdata as three sibling branches inside each workspace. core/workspaces.py::path() now returns <root>/documents instead of <root> itself; new root() gives the true workspace root. ark keeps working exactly as it did before - same .txt extension, same note/todo/evnt dirs, vendored binary completely untouched - just nested one level deeper on disk. real server data migrates automatically and idempotently on server startup (core/storage.py::_migrate_documents_layout(), same "check current shape, fix if needed, run every boot" convention as core/db.py's own schema fixups) - no manual script to run. media/ and appdata/ are not eagerly created (nothing writes to them yet) and are not git-tracked - see priority 1 above. verified: migration idempotency + empty-workspace handling, full Flask-test-client flow (new workspace creation, save, lock, documents scan, enable_git puts .git inside documents/ correctly), and a real dev-server run against a seeded old-layout directory - zero errors, migration fired correctly on real startup.

correction to phase 1 (2026-08-18): phase 1's "documents/" was the wrong name for that sibling - it read as one generic bucket shared across apps, when the actual intent was that any app with user-facing data gets a folder named after itself inside the workspace (so ark's data lives under a workspace's own ark/, not documents/). core/workspaces.py::path() now returns root()/<app> instead of root()/documents; core/storage.py's boot-time migration handles both the original flat pre-phase-1 layout and the short-lived documents/ layout, folding either into <app>/, idempotently. media/ and appdata/ (still unimplemented, see priority 1) are unaffected by this - this was purely a naming/location fix for the one sibling actually in use.

phase 2: SCRAPPED (2026-08-18). Considered redesigning ark to drop the note/todo/evnt/yyyy/mm structure in favour of one flat, .arkrc-configurable output folder with date-first batch filenames. Rejected after realising two things: (1) most notes are multiline, and multiline notes each get their own file rather than being batched (only oneline records get consolidated) - so "flat" would mean thousands of individual files in one folder over time, not a small number of batches, which is exactly the "ever-growing flat folder" problem the redesign was trying to avoid; (2) type-as-directory (note/todo/evnt) and date-as-directory (yyyy/mm) are separate axes that got conflated during the design discussion - only the type axis was actually in tension with ark's "data is the index" philosophy, and a full flat layout traded that problem for a worse one (bulk human/terminal browsability) without a real win.

  decision: ark's internal file structure is staying exactly as it is, permanently. note/todo/evnt/yyyy/mm directories, .txt extension, filenames are ark-generated (yyyymmddThhmmss.txt) or the title metadata property if set - none of this changes. this is a closed design question now, not an open one - don't relitigate scan-performance or flat-folder ideas for ark's own directory layout without a genuinely new argument. "the data is the index" (no cache/index, full live scan every query) is still the permanent philosophy for ark, just realised via the existing note/todo/evnt/yyyy/mm tree rather than a flat one.

  vendored ark (apps/ark/vendor, submodule of benjaminingreens/ark.git) and the real upstream repo at /home/benjamin/ark need no changes as a result of this decision - phase 2 never got past planning, no code was touched.

phase 3 (DONE, 2026-08-18): replaced Documents with Files, and - as an extra, related piece of work decided mid-implementation - extracted a generic Editor app (apps/editor/, HIDDEN so it never shows in the launcher/switcher) out of what used to be Ark's own embedded file view/edit/save/lock code. The view/edit/save/lock/autosave/vim-mode machinery was never actually Ark-specific, it just used to live inside apps/ark/ - it's now shared infrastructure any app links a user into via a file=/workspace=/app=/home= URL (apps/editor/routes.py::editor_workspace() resolves off the workspace row's own `app` column, not a hardcoded "ark", so it's reusable beyond Ark's workspaces too). Ark's result-list links and Files' file rows both hand off to it now; Ark kept its own command/query engine and record-highlighted result-card rendering unchanged (colorize_meta, still Ark-only). Files (apps/files/) is a clickable directory listing (not a tag browser) - `mkdir`/`touch`/`mv`/`rm [-r]` typed commands for mutations, everything else typed is a case-insensitive filename search; never parses ark record syntax, treats every file as opaque plain text; scoped to a workspace's documents/ only (media/ isn't written to by anything yet); reuses Ark's existing workspace DB rows (app="ark") rather than minting its own, and Ark's own `ark_workspace()` resolver directly, both required for file_locks to correctly collide between Ark/Files/Editor editing the same file. `.ark`/`.git` (and any other dotfile) are filtered out of every listing, search, and command target. `/apps/ark/conflicts` (git conflict resolution) stayed in Ark, unchanged, out of scope. `templates/_topbar.html`'s old multi-workspace-visibility checklist (Documents-only, dead once Documents was deleted) was removed rather than repointed. verified end-to-end against a real dev-server run: Ark add/query/tidy still work, note content opens correctly through Editor with meta-highlighting correctly gone (plain text, no color), save/lock/unlock persist to disk, mkdir/touch/mv/rm/rm -r all work and correctly refuse a non-empty dir without -r, path-traversal and dotfile-mutation attempts both 403, filename search works, and the app list/topbar correctly show Ark/Chat/Files/Settings with Editor never appearing - zero errors in the server log.
